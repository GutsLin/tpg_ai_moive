# 视频下载队列重构计划

> 创建时间：2026-08-26
> 当前线上版本：release `20260825-video-ref-limits`（r14）

## 背景

本轮排查发现视频任务端到端耗时的核心瓶颈：**轮询批次内串行下载视频**。一个批次最多 5 个任务（r14 已从 20 降到 5），下载串行执行，如果某个任务下载卡在网络黑洞，会拖住整个批次直到看门狗超时（3 分钟）。

当前参数（r14）：
- `VIDEO_DOWNLOAD_TIMEOUT_MS = 2 * 60_000`（单任务下载超时 2 分钟）
- `SYNC_RUN_TIMEOUT_MS = 3 * 60_000`（批次看门狗 3 分钟）
- `DEFAULT_SYNC_BATCH_SIZE = 5`（每批 5 个任务）
- `DEFAULT_SYNC_POLL_INTERVAL_MS = 30_000`（轮询间隔 30 秒）

## 问题

同步批次（`createVideoSyncProcessor`）把"查状态"和"下载+上传OSS"混在一起串行执行：
1. 批量调用 `listTasks` 查询上游状态
2. 对每个 completed 的任务**串行**下载视频 + 上传 OSS
3. 下载卡住 → 整个批次卡住 → 看门狗杀批次 → 其余任务轮询被跳过

## 重构方向

将"下载+上传"从同步批次中拆出，改为独立队列：

1. **同步批次只查状态**：`listTasks` → 更新 `lastArkStatus` → 对 completed 的任务写 `arkVideoUrl` 并标记 `download_prepared`
2. **下载走独立队列**：completed 的任务入队 `download-video`，并发下载（concurrency: 3-5）
3. **下载处理器**：fetch + arrayBuffer + putObject，失败重试逻辑不变（404/403 判终态，其余重试）

### 涉及文件

- `backend/src/workers/video.worker.ts`：拆分 syncProcessor，新增 downloadProcessor + downloadQueue
- `backend/src/services/video.service.ts`：`listSyncableArkTasks` SQL 条件可能需调整（download_prepared 状态的任务不再被 sync 查询）
- `frontend/src/pages/Videos/TaskCard.tsx`：子状态展示已就绪（r12 已上线）
- `tests/backend/video-workers.test.ts`：更新测试

### 数据库

`video_tasks` 表无需新增字段，复用现有 `last_ark_status` / `ark_video_url` / `video_oss_key` / `next_poll_at` 即可区分状态：
- `processing` + `last_ark_status != completed` → 在同步轮询队列
- `processing` + `last_ark_status = completed` + `video_oss_key IS NULL` → 在下载队列
