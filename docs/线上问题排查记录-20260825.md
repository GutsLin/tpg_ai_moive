# Narrix 线上问题排查与修复记录

> 日期：2026-08-25 ~ 2026-08-26
> 环境：生产（阿里云 8.156.73.136，release `20260825-video-ref-limits`）
> 涉及版本：r3 ~ r10 共 8 轮部署

---

## 问题一：视频生成"一直显示生成中"（任务永久卡死）

**现象**：任务长时间停在"生成中"，用户无法拿到结果。

**根因**（两层叠加）：
1. 轮询循环永久卡死：worker 下载结果视频的 `fetch` 无超时，一次网络挂起导致 `syncRunning` 锁永不释放，之后每 30 秒的轮询全部被跳过（日志连续 80+ 次 `skipped because previous run is still active`）
2. 孤儿任务：任务进入下载阶段时 `next_poll_at` 被置空，worker 崩溃后该任务既不满足轮询 SQL（要求 `next_poll_at IS NOT NULL`），也不被 reconcile 兜底（只处理无平台任务 ID 的任务），永久卡死

**修复**：
- 下载 fetch 加 `AbortSignal.timeout(10分钟)`
- 同步批次加 11 分钟看门狗（`Promise.race`），任何内部调用挂起都会释放锁
- reconcile 兜底：停滞任务若有平台任务 ID 但 `next_poll_at` 为空且无结果视频，自动恢复轮询时间
- 平台 API 请求（ark-bearer / toapis-avatar / ark-aksk 三处客户端）统一加 60 秒超时

**部署**：r3（参考素材上限）、r7（素材侧同款问题）

## 问题二：视频下载失败（files.toapis.com 域名 DNS 污染）

**现象**：上游已完成，但结果视频下载反复 `fetch failed`。

**根因**：ToAPIs 部分结果文件签发在 `files.toapis.com` 域名，该域名在国内被 **DNS 污染**（解析到 Facebook 的 IPv6 假地址），服务器完全无法连接。验证发现同一文件可通过 API 同域 `/__files/` 路径访问。

**修复**：下载前自动改写 URL——`https://files.toapis.com/videos/X` → `https://<平台当前域名>/__files/videos/X`（实测 14.5MB 文件 4 秒下载成功）。

**部署**：r4

## 问题三：旧任务轮询 5 天全部失败（endpoint 快照不一致）

**现象**：任务 28502 轮询 5 天全部 `fetch failed`。

**根因**：`getClientConfiguration` 的 endpoint 使用任务创建时的**快照值**（5 天前的 `toapis.com`，已被封），而 api_key 却取当前值——不一致导致旧任务永远请求死域名。

**修复**：endpoint 改用 provider 表**当前配置**（与 api_key 语义一致）。部署后 28502 在 40 秒内自动完成下载+上传 OSS（卡了 5 天的视频找回）。

**部署**：r5

## 问题四：前端参考素材上限一直是 9-3-3（配置不生效）

**现象**：后端配置已是 30/10/10，前端仍然只能选 9 张图。

**根因**：上限计算逻辑错误——兜底值被无条件计入取小运算：

```tsx
// 错误：Math.min(9, 30, 30) = 9，兜底值把配置压死了
Math.min(fallback, providerLimits, modelLimits)

// 正确：配置/模型上限存在时取较小值，都缺失才用兜底
candidates.length > 0 ? Math.min(...candidates) : fallback
```

**部署**：r6

**当前生效上限**（按 ToAPIs 文档）：

| 模型 | 图片 | 视频 | 音频 |
|---|---|---|---|
| Seedance 2.0 / 2.0 Fast | 9 | 3 | 3 |
| Seedance 2.5 | 30 | 10 | 10 |

## 问题五：素材库同步失败 fetch failed（无自愈机制）

**现象**：素材同步大量失败，状态落 `failed` 不会自动恢复。

**根因**：
1. 瞬时网络错误（fetch failed / 504）直接把素材标记为 `failed` 终态；BullMQ 仅重试 3 次（约 21 秒窗口），网络抖动超过即永久失败
2. 素材库客户端 fetch 无超时，可能挂起

**修复**：
- 瞬时错误识别（fetch failed/timeout/5xx/ECONNRESET/限流）：命中时保持 `pending` 等待重试，永久性错误（如尺寸非法）才落 `failed`
- 每 2 分钟 reconcile：停滞超 3 分钟的 pending/processing/deleting 素材自动补处理
- 素材库 API 加 60 秒超时

**部署**：r7

## 问题六：素材 processing / deleting 状态孤儿（审查发现，用户未直接报障）

**根因**：
- processing：素材创建后最多 2 分钟轮询期内 worker 崩溃，素材永久停在 processing（reconcile 原来只扫 pending）
- deleting：删除流程（OSS→远端→DB）中断后无恢复路径，素材永久卡在 deleting

**修复**：
- reconcile 扫描范围扩展到 pending + processing + deleting 三态
- 删除流程幂等化：远端删除失败不再阻断本地 DB 清理；残留远端素材由 reconcile 周期按幂等规则重推（OSS 已删 404 跳过、本地已删直接返回）

**部署**：r8

## 问题七：手动"重新拉取"的两个缺陷（审查发现）

**缺陷 A — 失败任务无限复活**：上游文件已过期（404）的失败任务可被无限翻回 processing，每次要等 24 小时超时才再失败。
**修复**：手动拉取时，若任务为 failed 且上游已完成但成品未取回，直接拒绝并提示"结果文件已无法取回，请重新生成"。

**缺陷 B — 无即时反馈**：手动拉取只写 `nextPollAt=now` 依赖 30 秒定时器，轮询循环被看门狗锁住期间（最长 11 分钟）操作无效果。
**修复**：同步队列 worker 从空实现改为真正的单任务同步处理器；手动拉取时立即入队一次该任务的同步（1 秒延迟）。

**部署**：r9

## 问题八：视频下载失败 478

**现象**：2026-08-26 凌晨起，7 个任务（后来确认共 29 个）下载返回 HTTP 478，全部落 failed 终态。

**根因**：478 是 `files.toapis.cn` 文件服务器的**瞬时错误**（临时抖动/限流），但代码把所有非 403 的下载失败都当永久失败处理。实测这些文件全部还在且可正常下载（直连 200，秒下）。

**修复**：下载失败分类处理——
- **404 / 403**：文件已过期/签名问题，重试无意义 → 标记失败提示重新生成
- **其余（478/5xx 等瞬时错误）**：文件通常还在 → 保持 processing 排下一轮重试，24 小时停滞超时兜底

另将 `files.toapis.cn` 也纳入 `__files` 域名改写（统一走 API 同域路径）。

**部署**：r10；存量 29 个失败任务已重置，自动补下载陆续出片中

## 附：所有问题的共同背景

服务器到 ToAPIs 平台（toapis.xyz 及其文件域名）的网络质量差且不稳定：DNS 污染、多 IP 轮换部分黑洞、瞬时 478/504。**本轮修复的总体思路不是修网络，而是让系统在这种网络下具备免疫力**：

1. 所有外部请求有超时（60s API / 10min 下载）
2. 所有锁有看门狗（最长 11 分钟自动释放）
3. 所有瞬时错误走重试而非终态（永久错误才判失败）
4. 所有中间状态有 reconcile 周期自愈（每 2 分钟）
5. 所有终态判定有 24 小时停滞超时兜底

若要根治网络问题，可考虑给服务器配置到 ToAPIs 的稳定代理出口，或在 ToAPIs 控制台反馈链路问题。
